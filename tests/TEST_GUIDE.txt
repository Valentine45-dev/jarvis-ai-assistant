R3-12 — Vision: different questions about the SAME image now get the
        right answer (cache no longer collides on image bytes alone)
-----------------------------------------------------------------------
READ FIRST — two traps that make this look like it "doesn't work":

  (a) The line JARVIS SPEAKS FIRST is just an acknowledgement, NOT the answer.
      "Taking a look at your screen now." / "Scanning the screen for the close
      button." are the pre-analysis lines. The real answer (the description /
      where the button is) is delivered AFTER, as the spoken follow-up. To also
      see the analysis TEXT on the Terminal page, set in Settings (or
      config/jarvis.json):  vision_show_analysis = true   then re-run.

  (b) You CANNOT trigger this bug with two screenshots of the live HUD. The bug
      only fires when two captures are byte-for-byte IDENTICAL. A running JARVIS
      screen is never identical (the arc reactor pulses, the clock ticks, TTS
      animates), so two screenshots always differ, never share a cache entry,
      and the cache path is never exercised. Screenshots prove nothing here.

RELIABLE test — use the SAME IMAGE FILE twice (a file's bytes ARE identical
every time it's loaded). Pick any image on disk, e.g. a reference PNG:
     C:\Users\Lenovo\Documents\jarvis-project\assets\reference\jarvis_main_hud.png

  1. Say / type:  "describe the image at <that full path>"
        -> JARVIS describes the picture. Note the answer.
  2. Say / type:  "what colours are in the image at <that same path>"
        (a DIFFERENT question about the SAME file)

PASS (fixed):
  - The second answer is about COLOURS, not a repeat of the first description.
  - Different questions on the same file give different, on-topic answers.

FAIL (old behaviour):
  - The second question returned the FIRST question's answer verbatim, because
    the cache key was the image bytes only and ignored the question.

Cache-still-works check:
  - Ask the SAME question about the SAME file twice -> the second returns
    instantly (cache hit) with the same answer. Proves we fixed the collision
    without disabling caching.

Code-level proof (no API key, no network) — run from the repo root; this drives
the real analyze_image() with byte-identical images and a fake client:
  uv run python -c "import core.vision as v; v.clear_vision_cache(); \
R=lambda t:type('R',(),{'content':[type('X',(),{'text':t})()]})(); \
C=type('C',(),{'messages':type('M',(),{'create':lambda s,**k:R('A: '+k['messages'][0]['content'][1]['text'][:40])})()})(); \
v._get_client=lambda:C; i=b'SAME-BYTES'; \
a=v.analyze_image(i,'close button','find_ui_element'); \
b=v.analyze_image(i,'what colour is the logo','answer_question'); \
print('different question -> different answer:', a!=b, '| cache entries:', len(v._vision_cache))"
  -> expect:  different question -> different answer: True | cache entries: 2

R3-11 — Reminders: listing reminders while one fires no longer crashes
-----------------------------------------------------------------------
Goal: have a reminder fire at the same moment you ask to list reminders.

Do this:
  1. Set several short reminders back to back, e.g.:
        "remind me to stretch in 5 seconds"
        "remind me to drink water in 6 seconds"
        "remind me to check email in 7 seconds"
  2. As those 5-7 seconds tick down, repeatedly say / type:
        "list my reminders"
     Fire it several times quickly so one "list" lands exactly as a reminder pops.

PASS (fixed):
  - "list my reminders" always returns a clean list (or "No active reminders.").
  - Reminders fire normally on the HUD. No error toast, no broken list.

FAIL (old behaviour):
  - Occasionally the list command errored out (internally a
    "dictionary changed size during iteration" crash) right as a reminder fired,
    so you'd get a generic failure instead of the list.

Note: this is a timing/race bug, so it was intermittent before. If you can't
make it collide by hand, just confirm listing works reliably while reminders
are active — the fix removes the crash window entirely.

R3-10 — kill_process: JARVIS won't kill itself, matches by exact name,
        and shows the full list before a broad kill
-----------------------------------------------------------------------
JARVIS runs as python.exe, so "kill python" used to kill JARVIS itself.

TEST A — self-protection (the important one):
  Say / type:  "kill the python process"   (or "kill process named python")
  When the confirmation card appears, confirm it (say "yes").

  PASS (fixed):
    - JARVIS stays open and running.
    - If python.exe processes other than JARVIS exist, only those are reported;
      JARVIS is never in the kill list.
    - If JARVIS is the only python process, you get "No process matching 'python'"
      (it excluded itself) — and JARVIS is still alive.

  FAIL (old behaviour):
    - JARVIS abruptly closed (it killed its own process), often mid-reply.

TEST B — exact name, not substring:
  Open Notepad (notepad.exe). Then say:  "kill the process named note"
  PASS (fixed): "No process matching 'note'" — "note" is not the real name.
                Now say "kill notepad" -> Notepad closes (exact name matches).
  FAIL (old): "note" as a substring of "notepad.exe" killed Notepad.

TEST C — broad-match safety list:
  Open two or three Notepad windows (each is its own notepad.exe), then say:
        "kill notepad"
  PASS (fixed): you get a SECOND confirmation that names every match, e.g.
        "3 processes match 'notepad': notepad.exe (PID ...), notepad.exe (PID ...)
         ... Kill all of them?"
        Confirm -> all close. (A single Notepad needs no extra prompt — it just
        closes after the normal kill confirmation.)
  FAIL (old): it silently killed everything matching with no list shown.

  By PID: "kill PID <JARVIS's own pid>" -> refuses with
          "Refusing to kill JARVIS's own process."  (find the pid in Task Manager).

R3-7 — Confirmation: a "no / wait / cancel" reply never triggers a
        destructive action, even if it also contains "yes"
-----------------------------------------------------------------------
Use any destructive command that shows a confirmation card. A safe one to test
with is creating then deleting a throwaway file, or just "shut down the computer"
(then DON'T actually confirm — use a cancelling reply).

Do this:
  1. Say / type something that asks for confirmation, e.g.:
        "delete the file test_throwaway.txt"   (create it first with
         "create a file called test_throwaway.txt")
     A confirmation card appears.
  2. Reply with a HEDGED / self-correcting answer that contains a "yes" word
     but also a negation, e.g.:
        "yes — wait, no"
        "sure, actually cancel"
        "no don't"

PASS (fixed):
  - JARVIS stands down ("Understood — standing down.") and does NOT delete.
  - The file is still there.

FAIL (old behaviour):
  - Because the reply contained "yes"/"sure", JARVIS treated it as approval and
    DELETED the file anyway.

Also verify normal flow still works:
  - A clean "yes" / "go ahead" / "do it" still confirms and deletes.
  - A bare "please" by itself NO LONGER counts as confirmation (it's too weak) —
    reply just "please" to a card and JARVIS should stand down, not proceed.

R3-14 — Workflows: editing a fetched workflow no longer corrupts the
        saved copy
-----------------------------------------------------------------------
This guards against the library handing out a shared reference to a workflow's
steps. Hard to trigger by normal voice use, so test via behaviour stability:

Do this:
  1. Create a workflow with a few steps, e.g.:
        "create a workflow called demo that opens chrome and takes a screenshot"
  2. Run it a few times:
        "run demo"   (repeat 3-4 times)
  3. Open the AUTOMATE page and inspect the "demo" workflow's step list.
        Also open data/workflows.json in an editor.

PASS (fixed):
  - The step list for "demo" is identical every time — same steps, same order,
    same count — no matter how many times you run it or list it.
  - data/workflows.json still shows exactly the steps you defined; no duplicated,
    mutated, or extra steps appear over repeated runs.

FAIL (old behaviour):
  - Repeated runs / inspections could mutate the in-memory workflow (steps getting
    normalised or appended in place), and a later save would persist the corrupted
    version to workflows.json.

Quick confidence check: "list my workflows" several times in a row — every
listing returns the same stable data.

R3-3 — Raw PowerShell / CMD now asks before running (and destructive
       cmdlets are caught), instead of running unconfirmed
-----------------------------------------------------------------------
Before this fix, "use PowerShell to ..." ran immediately. PowerShell-native
destructive cmdlets (Stop-Computer, Format-Volume, ...) slipped past the danger
check entirely and could power off / wipe with NO confirmation. Now EVERY
run_powershell / run_cmd asks first.

NOTE: keep AUTO_CONFIRM off for these. Also, if you've turned on
allow_ai_command_autorun, raw shell runs without asking by design — leave it OFF
to see the confirmation behaviour.

TEST A — benign PowerShell now confirms:
  Say / type:  "use PowerShell to get the date"   (or @code Get-Date)
  PASS (fixed): a confirmation card appears ("Run this PowerShell command? ...
                Get-Date") BEFORE anything runs. Say "yes" -> it runs and shows
                the date.
  FAIL (old):   it ran immediately with no confirmation.

TEST B — destructive cmdlet is caught (the important one — do NOT confirm):
  Say / type:  "use PowerShell to run Stop-Computer"
  PASS (fixed): a confirmation card appears. Reply "no" / "cancel" -> JARVIS
                stands down and the PC stays on.
  FAIL (old):   the machine powered off with no prompt.
  ⚠ Do NOT confirm this one. Same goes for Restart-Computer, Format-Volume,
    Clear-Disk — they're now in the denylist; verify the CARD appears, then cancel.

TEST C — CMD also confirms:
  Say / type:  "use CMD to run ipconfig"
  PASS (fixed): confirmation card appears first; confirm -> it runs.

TEST D — single confirmation, not double (for a destructive one):
  "use PowerShell to run Stop-Computer" -> you should see exactly ONE card, not
  two (the fix reuses the danger-confirm gate so it doesn't prompt twice). Cancel it.

Code-level proof (no execution, no shutdown) — from repo root:
  uv run python -c "import core.handlers.code_exec as ce; \
print('benign PS confirms :', ce._handle_code_execution('run_powershell',{'code':'Get-Date'}).get('needs_confirmation')); \
print('Stop-Computer caught:', ce._danger_check('Stop-Computer') is not None)"
  -> both print True.

R3-1 / R3-2 - Workflows: no re-entrant dispatch (a running workflow
        blocks new commands; a cron fire is dropped while busy)
-----------------------------------------------------------------------
Background: workflow steps run on the UI thread and pump the event loop
between steps. Before this fix a command typed mid-workflow - or a
scheduled (cron) workflow firing while another was running / a card was
up - could re-enter dispatch and overlap or corrupt the running workflow,
or replace a confirmation card out from under you. Now a workflow marks
itself "in flight" and both entry points respect it: _process_cmd rejects
new commands, and _on_scheduled_workflow_fire drops the cron fire.

NOTE: keep AUTO_CONFIRM OFF so the confirm step in TEST B actually pauses.
Turn DEBUG on to see the "skipped - JARVIS busy" scheduler log in TEST C.

TEST A - a new command is rejected while a workflow runs:
  1. Run a multi-step workflow that takes a few seconds, e.g. say / type:
        "open chrome and search youtube for lofi and take a screenshot"
     (the brain calls between steps give you a 1-2 s window).
  2. While it's mid-run (HUD shows "Automation: step 2/3" etc.), quickly
     type another command in the command bar, e.g. "what time is it".
  PASS (fixed): a toast "A workflow is running - please wait." appears and
                the second command does NOT run. The workflow finishes its
                own steps cleanly, in order.
  FAIL (old):   the typed command dispatched in the middle of the workflow
                (interleaved steps, doubled output, or a corrupted run).

TEST B - a workflow that pauses on a confirm still resumes (regression
         guard for the in-flight COUNTER - the important one):
  1. Run a workflow whose steps include a file creation, e.g.:
        "create a file called wf_test.txt then open chrome"
  2. It pauses on the create-file confirmation card.
  3. Reply "yes" (typed or spoken).
  PASS (fixed): the file is created AND the workflow resumes and finishes
                the remaining steps (chrome opens). The "yes" is NOT blocked
                by the "workflow is running" toast - it resolves the card,
                and the resume frame is still counted as in-flight.
  FAIL (broken): the "yes" is rejected as a new command, or the workflow
                never resumes after the confirm (a plain bool flag instead
                of a counter would clear early here and break the resume).
  Cleanup: delete wf_test.txt afterwards.

TEST C - a scheduled (cron) workflow is dropped while JARVIS is busy:
  1. Create a workflow on a 1-minute schedule, e.g.:
        "create a workflow called ping that takes a screenshot, every minute"
     (cron "* * * * *").
  2. Keep JARVIS busy as the minute ticks over - start a second, slower
     manual workflow, or trigger any confirmation card and leave it open.
  PASS (fixed): the scheduled "ping" does NOT fire on top of the busy state.
                With DEBUG on you'll see a log line like:
                  [scheduler] scheduled workflow 'ping' skipped - JARVIS busy (state=...)
                The next minute, when idle, it fires normally.
  FAIL (old):   "ping" fired mid-confirmation / mid-workflow, overlapping
                dispatch and possibly replacing the open card.
  Cleanup: "delete the workflow ping" when done.

Code-level proof (no UI, no cron) - from repo root; drives a real workflow
with a fake dispatch and asserts the in-flight flag is True during each
step and False after:
  uv run python -c "import core.executor as ex, core.handlers.automation_handler as ah; \
seen=[]; ex.dispatch=lambda step,**k: (seen.append(ah.is_workflow_in_flight()), {'success':True,'response':'ok','intent':step.get('intent','x')})[1]; \
wf={'task_name':'t','steps':[{'intent':'open_app','action':'open_browser','parameters':{}},{'intent':'system_control','action':'screenshot','parameters':{}}]}; \
out=ah._handle_automation_task('run_workflow',wf); \
print('in-flight during steps:', seen, '(want [True, True])'); \
print('in-flight after return :', ah.is_workflow_in_flight(), '(want False)')"
  -> expect:  in-flight during steps: [True, True] ... after return: False

R3-8 / R3-9 - Scheduler: no double-fire on restart, and catch-up for a slot
        missed while JARVIS was closed (or the machine was asleep)
-----------------------------------------------------------------------
Background: the scheduler now persists the last *scheduled instant* it fired
per workflow to data/scheduler_state.json. That kills the restart double-fire
(R3-8) and lets a tick after downtime catch up a missed slot (R3-9). From the
scheduler's point of view "machine asleep" and "JARVIS closed" are the same
thing - no tick runs - so closing the app is a faithful way to test both.

Setup (used by both tests):
  Create a per-minute workflow that leaves an obvious trace each time it fires:
     "create a workflow called ping that takes a screenshot and saves it to
      C:\Users\Lenovo\Documents\jarvis-project\tests, every minute"
  Make sure it's enabled (ENABLED ON in the AUTOMATE page, or say "enable ping").
  Each fire = one new JARVIS_<date>_<time>.png in tests\ AND a console line:
     [scheduler] firing workflow 'ping' (schedule='* * * * *')
  Keep the PS console visible. Clean up the screenshots when done.

TEST A - R3-8: no double-fire when you restart within the same minute
  1. Watch the console; wait for ONE "firing workflow 'ping'" line (note the
     minute, e.g. 02:41, and that one screenshot appeared).
  2. IMMEDIATELY - still within that same minute - close JARVIS and restart it
     (uv run python main.py).
  PASS (fixed): during the rest of that same minute, ping does NOT fire again -
                no second screenshot for that minute, no second "firing" line.
                On the next minute boundary it fires once, normally.
  FAIL (old):   ping fired a second time for the same minute right after restart
                (the in-memory guard was empty on a fresh start).
  Proof on disk: open data\scheduler_state.json - it has a "ping" entry with the
                 last-fired ISO instant; that's what survived the restart.

TEST B - R3-9: catch-up for a slot missed while JARVIS was closed/asleep
  1. Let ping fire at least once (so it has a recorded last-fired instant).
  2. Close JARVIS. Leave it closed for 2-3 minutes (this is the "asleep over the
     scheduled slot" condition - several per-minute slots pass with no tick).
  3. Reopen JARVIS (uv run python main.py) and watch the console.
  PASS (fixed): within a few seconds of startup you get exactly ONE "firing
                workflow 'ping'" line (one catch-up screenshot) for the most
                recent missed minute - NOT one per missed minute. Then it
                resumes firing once per minute.
  FAIL (old):   nothing fired to make up the missed slot (it was silently lost);
                "every day at 9" would simply not run if asleep at 9.
  Storm-safety note: even if you leave it closed for an hour, reopening fires
                ONCE (the latest missed slot), never a backlog flood.

  (A daily "30 9 * * *" behaves the same - it just takes a day to exercise by
   hand, which is why the per-minute proxy above is the practical test. For the
   exact instant logic without waiting, run the automated proof below.)

Code-level proof (no waiting, no restart) - from repo root:
  uv run pytest -q tests/test_scheduler_catchup.py
  -> 12 passed: restart-same-minute no double-fire, catch-up after downtime,
     per-minute advance, long-downtime collapses to one fire, persistence
     round-trip, and frozen-clock _tick integration.

R3-15 / R3-16 / R3-17 - Wake word: clean mic handoff, no recognition gap,
        and a visible warning when speech recognition goes offline
-----------------------------------------------------------------------
Background: the always-on wake detector now (R3-17) recognises on a separate
thread from capture, so the mic keeps listening during the network call;
(R3-16) classifies STT errors and warns once if recognition keeps failing
instead of dying silently; and (R3-15) hands the mic off to the main capture
with a real "stream closed" event instead of a fixed sleep.

These run on real mic + network, so most of the verification is "does the wake
word still work smoothly?" The exact logic is covered by the automated proof at
the bottom - run that first; the manual checks below are for the live feel.

Setup: turn DEBUG on (Settings or .env DEBUG=true) so the [wake] log lines show.
Keep the PS console visible.

TEST A - R3-17: wake word still triggers reliably, including back-to-back
  1. With JARVIS idle, say "Jarvis" - the orb should switch to listening.
  2. Let it go back to idle, then say "Jarvis" again a few times at a normal
     pace, including right after it returns to idle.
  PASS (fixed): each "Jarvis" is caught; you don't have to repeat it because it
                "wasn't listening yet". In the log you'll see [wake] heard: ...
                lines appearing continuously (capture never stalls for the STT
                call).
  FAIL (old):   some "Jarvis" said while it was mid-recognition were missed.
  Note: this is probabilistic - the old gap was intermittent, so "it just works
        every time now" is the signal. The automated test pins the mechanism.

TEST B - R3-15: no mic conflict on the handoff
  1. Rapidly trigger listening several times: say "Jarvis", let it idle, repeat
     quickly; or use the mic button repeatedly.
  PASS (fixed): listening opens cleanly each time; no bursts of "no speech" /
                device-busy errors in the log. You may see a one-off
                [voice] wake stream-closed wait timed out; proceeding - that's
                the safe fallback, not an error.
  FAIL (old):   intermittent capture failures / "no speech" right after a wake,
                from two streams briefly sharing the mic device.

TEST C - R3-16: offline warning is visible (optional, needs forcing a failure)
  Easiest way to force persistent STT failure: disconnect the network (turn off
  Wi-Fi) and then make noise near the mic so the detector runs STT on non-silent
  windows.
  PASS (fixed): after ~5 consecutive failed recognitions you get ONE toast:
                "Wake word offline - speech service unavailable." (and a [wake]
                warning line). It does NOT spam - just once. Reconnect Wi-Fi and
                the next successful recognition silently re-arms the warning.
  FAIL (old):   wake word just stops working with nothing in the log or UI.
  (Skip if you don't want to toggle Wi-Fi - the automated test covers the
   threshold + warn-once + reset logic exactly.)

Code-level proof (no mic, no network) - from repo root:
  uv run pytest -q tests/test_wake_word.py
  -> 11 passed: STT error classification (benign vs counted), warn-once at the
     threshold + reset on success, recognise/wake-match/paused-skip paths, and
     the stream-closed handshake event semantics.
